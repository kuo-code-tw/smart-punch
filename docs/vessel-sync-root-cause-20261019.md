# 船舶同步持續逾時調查（2026-10-19）

## 已確認

1. 截圖中的「超過60秒」來自前端總流程計時器，不是 Apps Script 執行例外。此前計時器把仍在等待的流程設為失敗，會誤判較慢但仍可能成功的同步。
2. `docs/combined-release-gate-20261017.md` 的正式讀取驗證記錄為 gcGetData 23,175／24,101 ms。10/19 前端曾將手動前置讀取、讀回設為15秒，逾時結果核對設為12秒；這些期限小於已知成功冷讀取耗時，容易產生假失敗。
3. 原流程可能依序讀取目前月份、補讀完整資料、核對前次寫入、上傳、讀回，以及因差額再補讀一次完整資料。各步都有期限，不代表整體能在60秒內結束。
4. 待同步一筆是佇列工作，不是一列資料。gcSyncAll 會送出 groups、assignments、records、shipMasters 的整批快照；須分開呈現批次數、明細數與船舶數。

## 本次修正

- 手動整批寫入前直接讀完整資料一次，採單次35秒讀取期限，不先讀月份再改讀完整資料。35秒是依既有實測調整的預算，不是後端速度改善證明。
- 核對未確認寫入時重用剛取得的完整快照，避免相同 GET 重複執行。僅未知結果核對可省略重送；新的正常寫入仍須取得正式 ACK。
- 寫入後讀回完整資料一次；完整資料已讀回時，不因數值差額再重抓同一包資料。數值不一致仍保留原核對警示。
- 超過總流程60秒只提示目前階段較慢，不再當作後端寫入失敗。真正單次讀取／寫入期限與取消保護仍保留。
- 錯誤明細記錄階段、逐段耗時、批次數、明細數與船舶數，不記 token、網址、姓名或資料內容。
- 未確認寫入仍保留佇列並停止自動重送；不能以數量相同代替內容核對，備註與巢狀資料差異同樣不能誤作完成。
