# GPS 額外打卡地點 — 正式 Apps Script 後端修復清單（2026-11-10）

## 已證實與未證實

- 考勤前端有五組 `extraLocations`（`name, lat, lng, radius`）。
- `saveSystemSettings()` 送出 `POST action=syncConfig`；正式回傳有時為 `signal is aborted without reason`。
- `GET action=getData` 讀回的定位設定未與新增設定一致，前端因此拒絕將未確認地點視為正式可打卡區域。
- 上述現象**無法單靠瀏覽器錯誤判斷**是寫入超時、資料未落盤、`getData` 遺漏欄位，或 GAS 快取讀到舊資料。
- GitHub 倉庫**沒有正在運行的正式 `Code.gs` 完整來源**，Google Drive 可見檔案中也沒有可直接修改的 Apps Script 專案。因此提交本文件與前端程式，不等於已修改正式 GAS。

## 正式 GAS 必須一起檢查的兩條路徑

### `syncConfig`（寫入）

1. 在現有管理員授權驗證後處理；不要新增繞過權限的公開寫入端點。
2. 確認 `data.config.extraLocations` 在入站接收、欄位白名單、儲存序列化、正式資料庫／PropertiesService 寫入、讀回每一步均未被丟棄。
3. 最多五筆。具名地點必須有緯度 -90..90、經度 -180..180、允許半徑大於 0；空白地點維持停用。**不得**將空值座標當成 `0,0`。
4. 無 `extraLocations` 欄位的舊客戶端更新，不可順手清空伺服器既有五筆。應在目前正式設定上合併有提供的欄位。
5. 儲存後從**同一個權威持久化來源**重新讀取，回覆 `ok:true` 前核對主要地點與五個額外地點完整一致。
6. `syncConfig` 不應為修改少量定位資料而執行整批考勤、班表或員工資料初始化／歸檔。檢查是否卡在 GAS 全域 ScriptLock、長時間 SpreadsheetApp 操作或重複的背景同步。

### `getData`（讀取）

1. 回傳目前正式儲存來源的 `config.locationName, lat, lng, radius, extraLocations`，包含五筆順序、名稱、經緯度與半徑。
2. 若 `getData` 有 CacheService 或其他快取，`syncConfig` 成功後必須使其失效，避免剛儲存完卻讀到舊值。
3. 不要為了回傳 GPS 設定而對一般打卡員工暴露管理憑證、管理員識別碼或其他私有設定；僅沿用原本公開可打卡的設定範圍。
4. `getData` 不應靜默以本機/程式預設值覆蓋正式保存的 `extraLocations`。

## 上線驗收

- 使用測試地點「空櫃堆高機」，緯度 `22.555499`，經度 `120.337724`，半徑 `100` 公尺；**切勿在正式服務上以此座標作假打卡**。
- 驗證新增後，從不同瀏覽器獨立 GET 讀回完全相同；重整頁面仍存在。
- 更改第二個地點，五筆順序與未修改地點保持不變。
- 使用舊客戶端只修改公司名稱後，五個 GPS 地點不得遺失。
- 模擬 POST 回覆丟失：若伺服器已寫入，讀回應可確認成功；若未寫入，前端必須保留輸入、拒絕啟用未核准地點。
- 一般員工定位打卡在每個地點只依正式設定的半徑判定，不得因新增/變更而繞過 GPS 檢查。
- 不修改既有考勤、請假、班表、人資或出勤歷史資料。

## 更新正式部署

備份**目前正式** Apps Script `Code.gs`、部署版本與綁定試算表；只對新鮮來源修補。先在測試副本進行 `syncConfig/getData` 寫入與獨立讀回測試，再用「部署 → 管理部署作業 → 編輯現有部署 → 新版本」發佈，保持既有 URL 和權限。切勿用 GitHub Pages 的成功部署取代 GAS 部署；若驗收失敗，回復前一 GAS 部署版本。

前端版本 `2026.11.10.115` 會保留失敗時的輸入，但僅在雲端已讀回核對後才啟用 GPS 設定。要完成真正的修復，需要從正式 Apps Script 專案取得最新的 `Code.gs`，檢查原本的設定持久化實作後再做最小範圍改動。
